1. INTRODUCTION                                         *gauntlet-introduction*

gauntlet.nvim reviews GitHub pull requests without leaving Neovim.

A review currently shows the conversation part of the pull request -- the
description its author wrote -- in a read-only window.  Diffs and comment
threads are still to come.

==============================================================================
2. REQUIREMENTS                                         *gauntlet-requirements*

  - Neovim 0.9 or newer.
  - The GitHub CLI, `gh`, on your PATH and authenticated.  gauntlet.nvim makes
    no GitHub requests of its own; it borrows gh's credentials.  Check with: >

    gh auth status
<
==============================================================================
3. INSTALLATION                                         *gauntlet-installation*

With lazy.nvim: >lua

    {
      "Loki-Astari/gauntlet.nvim",
      cmd = "Gauntlet",
      config = function()
        require("gauntlet").setup({})
      end,
    }
<
==============================================================================
4. COMMANDS                                                 *gauntlet-commands*

                                                                    *:Gauntlet*
:Gauntlet {id}          Review the open pull request {id} of the current
                        repository.  {id} may be written `142` or `#142`.

:Gauntlet {url}         Review the pull request named by a GitHub URL of the
                        form `https://github.com/{user}/{repo}/pull/{id}`.
                        Any trailing path, such as `/files`, is ignored.
                        The URL must name a remote of the repository you are
                        in; see |gauntlet-errors|.

:Gauntlet               List the open pull requests of the current repository
                        and choose one to review.

                        The list is presented through |vim.ui.select()|, so an
                        installed picker -- Telescope, fzf-lua, snacks.nvim --
                        is used automatically.

==============================================================================
5. THE TERMINAL COMMAND                                          *gauntlet-vig*

`bin/vig` ("nvim gauntlet") offers the same from a shell.  Put `bin/` on your
PATH, or alias it: >bash

    alias vig='~/.local/share/nvim/lazy/gauntlet.nvim/bin/vig'
<
                                                                         *vig*
vig {id}                Start Neovim with the review of pull request {id}
vig {url}               already open.
vig                     Print the open pull requests to standard output.
                        Neovim is not started.

Everything happens before an editor appears.  With an argument, vig runs the
whole of |gauntlet-worktree| headlessly first: it checks the argument, asks
GitHub about the pull request, fetches it, checks it out, and works out what
it changes.  Only then does Neovim start, and it is handed the finished review
rather than repeating any of it.

So every way this can fail -- a bad argument, a closed pull request, no
network, a repository too shallow to find the merge base, nowhere to put the
worktree -- is a line on standard error and a non-zero exit, with no Neovim
left running and no half-open review.

The review is opened once startup has finished, not during it.  Neovim runs
"-c" commands *before* |VimEnter|, so a config that restores a session there,
or opens a dashboard or a file tree, would otherwise land on top of the review
and replace it.  If your config does restore a session, `vig {id}` gives you
that session with the review as an extra, focused tab.

                                                          *$GAUNTLET_PRELOAD*
$GAUNTLET_PRELOAD is set for the whole life of a Neovim that vig started, so a
config can tell that this one exists only to show a review: >lua

    if vim.env.GAUNTLET_PRELOAD then return end
<
Two places are worth guarding that way if you save and restore sessions per
directory.  Skipping the *restore* keeps `vig {id}` to the review alone.
Skipping the *save* matters more: a review is a scratch buffer, not a
workspace, so a session written when vig exits would replace the real session
for that directory with nothing worth restoring.

$GAUNTLET_NVIM overrides the Neovim executable vig uses.

6. THE REVIEW VIEW                                            *gauntlet-review*

A review is one tab page: the changed files on the left, and on the right
either the pull request's description or a two-pane diff.
>
    +- Files ---------+- lua/gauntlet/ui.lua ---------------+
    | > Conversation  |  base             |  head            |
    |                 |                   |                  |
    | M .gitignore +3 |  local M = {}     |  local M = {}    |
    | A CLAUDE.md +54 |                   | +function M.pick |
    +-----------------+-------------------+------------------+
<
The file list is flat and sorted, each line carrying the status letter git
gives it -- A, M, D, R -- and the lines added and removed.  `Conversation` is
the first entry, so the description is one keystroke away from any file.

    <CR>                Open the entry under the cursor.
    q                   Close the review.
    <C-w>f              Jump back to the file list.

Selecting a file shows the merge-base version on the left and the pull
request's version on the right, in Neovim's own diff mode, so |]c|, |[c| and
|zo| all behave as they do in `vimdiff`.

An added file has an empty left-hand side, a deleted file an empty right-hand
side.

                                                        *gauntlet-read-only*
Everything is read-only.  The right-hand side is a real file in the review
worktree, which is what lets a language server, |gd| and |K| work on it, but
it is opened non-modifiable: reviewing must not be able to change a checkout.

==============================================================================
7. THE REVIEW WORKTREE                                      *gauntlet-worktree*

A review is backed by a git worktree, so that it can be *started* online and
*finished* offline.  Opening a review does all the network work at once:
>
    git fetch origin refs/pull/<n>/head     the pull request's commits
    git merge-base <base> <head>            what it branched from
    git worktree add --detach <dir> <ref>   its files, on disk
    git diff <base> <head>                  every blob of both sides
<
That last step matters on a partial clone -- one made with `--filter` -- where
blobs are otherwise fetched only when something asks for them, and a review
would quietly need the network for every file opened.

Afterwards the file list and both sides of every diff are read from local git.

A review is kept at: >

    ~/.local/state/nvim/gauntlet/<repo>/pr-<n>/
        worktree/       the checkout, detached at the pull request's head
        meta.json       base and head commits, and when they were fetched
<
The worktree is a *subdirectory* of the review rather than the review itself,
so that nothing gauntlet writes ever appears in the worktree's `git status`,
where it could be committed by accident.

Reviews persist.  Opening one again reconnects to what is already on disk and
needs no network at all.

                                                             *:GauntletDiscard*
:GauntletDiscard        Remove the current review from disk: its worktree, its
                        `refs/gauntlet/pr/<n>` ref, and gauntlet's own files.
:GauntletDiscard {id}   The same, for a review you are not looking at.

==============================================================================
8. ERRORS                                                     *gauntlet-errors*

A review is labelled "PR Review {id}".  Neovim's own tabline and bufferline
style plugins both label from the tail of a buffer's name, so that is the tail
of the name; the repository is kept in front of it to stay unique, since two
repositories can each have a pull request #1.  The tab also carries the label
in the tab-scoped variable `t:gauntlet_title`.

The review takes a tab page of its own, leaving your window layout untouched.
The exception is when the only thing on screen is Neovim's own empty starting
buffer -- which is what |vig| leaves behind -- and the review takes that over
instead, rather than stranding a blank "[No Name]" tab beside itself.

The buffer is read-only, 'buftype' "nofile", and 'filetype' "markdown".

    q                   Close the review.  This closes its window, and so its
                        tab page; if the review was all that was open, as
                        after `vig {id}`, Neovim exits.


Both `:Gauntlet` and `vig` report:

  - Not inside a git repository.
  - The repository has no *open* pull request with that id.  A pull request
    that is merged or closed is reported the same way as one that never
    existed.
  - A URL that names a repository which is not a remote of the current one.
  - An argument that is neither a number nor a pull request URL.

Having no open pull requests at all is *not* an error: the list is empty.

A bare {id} is looked up against the repository's `upstream` remote if it has
one, and `origin` otherwise, so that working from a fork reviews the pull
requests of the project you forked.

==============================================================================
9. CONFIGURATION                                       *gauntlet-configuration*

setup() takes an options table, merged over the defaults: >lua

    require("gauntlet").setup({
      gh = "gh",   -- path to the GitHub CLI
      limit = 100, -- most open pull requests to list at once
      dir = nil,   -- where review worktrees are kept; nil means
                   -- stdpath("state")/gauntlet
    })
<
Calling setup() is optional; the defaults apply without it.
