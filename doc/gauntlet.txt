1. INTRODUCTION                                         *gauntlet-introduction*

gauntlet.nvim reviews GitHub pull requests without leaving Neovim.

A review currently shows the conversation part of the pull request -- the
description its author wrote -- in a read-only window.  Diffs and comment
threads are still to come.

==============================================================================
2. REQUIREMENTS                                         *gauntlet-requirements*

  - Neovim 0.9 or newer.
  - The GitHub CLI, `gh`, on your PATH and authenticated.  gauntlet.nvim makes
    no GitHub requests of its own; it borrows gh's credentials.  Check with: >

    gh auth status
<
==============================================================================
3. INSTALLATION                                         *gauntlet-installation*

With lazy.nvim: >lua

    {
      "Loki-Astari/gauntlet.nvim",
      cmd = "Gauntlet",
      config = function()
        require("gauntlet").setup({})
      end,
    }
<
==============================================================================
4. COMMANDS                                                 *gauntlet-commands*

                                                                    *:Gauntlet*
:Gauntlet {id}          Review the open pull request {id} of the current
                        repository.  {id} may be written `142` or `#142`.

:Gauntlet {url}         Review the pull request named by a GitHub URL of the
                        form `https://github.com/{user}/{repo}/pull/{id}`.
                        Any trailing path, such as `/files`, is ignored.
                        The URL must name a remote of the repository you are
                        in; see |gauntlet-errors|.

:Gauntlet               List the open pull requests of the current repository
                        and choose one to review.

                        The list is presented through |vim.ui.select()|, so an
                        installed picker -- Telescope, fzf-lua, snacks.nvim --
                        is used automatically.

==============================================================================
5. THE TERMINAL COMMAND                                          *gauntlet-vig*

`bin/vig` ("nvim gauntlet") offers the same from a shell.  Put `bin/` on your
PATH, or alias it: >bash

    alias vig='~/.local/share/nvim/lazy/gauntlet.nvim/bin/vig'
<
                                                                         *vig*
vig {id}                Start Neovim with the review of pull request {id}
vig {url}               already open.
vig                     Print the open pull requests to standard output.
                        Neovim is not started.

Everything happens before an editor appears.  With an argument, vig runs the
whole of |gauntlet-worktree| headlessly first: it checks the argument, asks
GitHub about the pull request, fetches it, checks it out, and works out what
it changes.  Only then does Neovim start, and it is handed the finished review
rather than repeating any of it.

So every way this can fail -- a bad argument, a closed pull request, no
network, a repository too shallow to find the merge base, nowhere to put the
worktree -- is a line on standard error and a non-zero exit, with no Neovim
left running and no half-open review.

The review is opened once startup has finished, not during it.  Neovim runs
"-c" commands *before* |VimEnter|, so a config that restores a session there,
or opens a dashboard or a file tree, would otherwise land on top of the review
and replace it.  If your config does restore a session, `vig {id}` gives you
that session with the review as an extra, focused tab.

                                                          *$GAUNTLET_PRELOAD*
$GAUNTLET_PRELOAD is set for the whole life of a Neovim that vig started, so a
config can tell that this one exists only to show a review: >lua

    if vim.env.GAUNTLET_PRELOAD then return end
<
Two places are worth guarding that way if you save and restore sessions per
directory.  Skipping the *restore* keeps `vig {id}` to the review alone.
Skipping the *save* matters more: a review is a scratch buffer, not a
workspace, so a session written when vig exits would replace the real session
for that directory with nothing worth restoring.

$GAUNTLET_NVIM overrides the Neovim executable vig uses.

6. THE REVIEW VIEW                                            *gauntlet-review*

A review is one tab page: the changed files on the left, and on the right
either the pull request's description or a two-pane diff.
>
    +- Files ---------+- lua/gauntlet/ui.lua ---------------+
    | > Conversation  |  base             |  head            |
    |                 |                   |                  |
    | M .gitignore +3 |  local M = {}     |  local M = {}    |
    | A CLAUDE.md +54 |                   | +function M.pick |
    +-----------------+-------------------+------------------+
<
The file list is flat and sorted, each line carrying the status letter git
gives it -- A, M, D, R -- and the lines added and removed.  `Conversation` is
the first entry, so the description is one keystroke away from any file.
>
    M lua/gauntlet/ui.lua      ●2  +58 −45
    A tests/send_spec.lua         +193  −0
<
                                                        *gauntlet-file-list*
Its columns are measured once over the whole list and the numbers are right
aligned, so they end together and can be compared down the column.  The
counts sit against the right edge; the marker column appears only when some
file carries a thread, and takes its room from the path.

A path too long for the room left has its directories shortened to their
first letter -- `l/g/ui.lua` -- which keeps every part of the tree in view
where cutting the front off would not.  Only if that still will not fit is
the end kept, the filename being the part worth reading.

    <CR>                Open the entry under the cursor.
    q                   Close the review.
    <C-w>f              Jump back to the file list.

Selecting a file shows the merge-base version on the left and the pull
request's version on the right, in Neovim's own diff mode, so |]c|, |[c| and
|zo| all behave as they do in `vimdiff`.

An added file has an empty left-hand side, a deleted file an empty right-hand
side.

                                                        *gauntlet-read-only*
Reviewing someone else's pull request can alter nothing.  The right-hand side
is a real file in the review worktree, which is what lets a language server,
|gd| and |K| work on it, but it is opened non-modifiable: reviewing must not
be able to change a checkout.

Your own pull request is the exception -- see |gauntlet-author|.  The
left-hand side is the base, and is never writable by anyone.

The panes stay out of the buffer list, and are discarded as you move on, so a
review leaves nothing behind in |:ls|, |CTRL-^| or a bufferline plugin -- a
pane is furniture, not a file you opened.  A buffer you have split off into
another tab page yourself is left alone.

7. COMMENTS                                                 *gauntlet-comments*

    c                   Comment on the line under the cursor.
    dc                  Delete the comment on the line under the cursor.

`c` opens a buffer under the diff to write in.  It is an ordinary buffer, so
every editing habit works: `:w` keeps the comment, `:q` throws it away.  The
code being commented on stays in view above.

A line carrying a comment is marked in the sign column and highlighted, and
the comment is drawn underneath it as a bordered note, wrapped to fit.  The
file list counts them, so `●2` beside a file means two.

                                                        *gauntlet-highlights*
Colours are these groups, each defined only as a default, so anything a
colourscheme or your config sets wins.  The note:

    GauntletComment          the comment text     (NormalFloat)
    GauntletCommentBorder    the box around it    (FloatBorder)
    GauntletCommentAuthor    who wrote it         (Title)
    GauntletCommentSign      the marker and line  (DiagnosticSignInfo)

And the file list:

    GauntletStatusAdded      the A of an added file      (Added)
    GauntletStatusModified   the M of a modified one     (Changed)
    GauntletStatusDeleted    the D of a deleted one      (Removed)
    GauntletStatusRenamed    the R or C of a moved one   (Changed)
    GauntletAdded            the lines added, +58        (Added)
    GauntletRemoved          the lines removed, −45      (Removed)
    GauntletThread           threads still open, ●2      (DiagnosticSignInfo)
    GauntletSettled          threads dealt with, ✓1      (Comment)
    GauntletPathDir          the directory of a path     (Comment)
    GauntletPathFile         the filename                (Normal)

`Added`, `Changed` and `Removed` are Neovim's own groups for this, and colour
the text.  `DiffAdd` and its siblings colour the *background*, which would put
the status letter in a block rather than tinting it.

They link to the floating-window groups because that is the effect wanted: a
note laid over the code rather than another part of it.

The writing buffer spans both diff panes, so a comment has the full width of
the file to be written in, and both sides of the diff stay in view above it.

Comments anchor to a line *and a side*: the left-hand pane is the base, the
right-hand pane the pull request.  GitHub will only accept a comment on a line
that is part of the diff, so `c` refuses a line that is not, rather than
letting the rejection turn up later as a puzzle.

                                                       *gauntlet-threads*
The pull request's existing review threads are fetched when a review is first
prepared, and cached, so other people's comments are there offline too.  They
are drawn like your own, titled `thread` and naming who wrote each comment.

    T                   Show or hide resolved and outdated threads.

Resolved threads, and ones pinned to code the pull request has since changed,
start hidden -- as they do on GitHub -- so that a long argument settled last
week does not bury the diff.  The file list counts them apart: `●2` is two
still open, `✓1` one settled.  A thread about a whole file rather than a line
is counted but never drawn, having no line to sit against.

                                                           *:GauntletRefresh*
:GauntletRefresh        Bring the review up to date with GitHub.

Everything else a review does is answered from disk, which is what lets one be
finished with no network -- and what leaves it on the commit it was opened at.
This is the one command that goes and looks.  It fetches:

  - the pull request's branch again, and moves the worktree onto whatever its
    head is now, so commits pushed since the review started come into view;
  - the file list and both sides of every diff, recomputed against the new
    head and its merge base;
  - the comment threads.

The file you are looking at stays on show, followed by its path rather than by
its place in the list, since a new commit can add or drop files above it.  One
the new head no longer touches has nothing left to show, so the review falls
back to the conversation.

A failed thread fetch leaves the cache alone -- a bad connection must not cost
you the threads you had -- and the new commits are shown regardless.  Comments
you have drafted are kept, still anchored to the line and side you wrote them
against; check them if the code under them has moved.

Fetched threads are read-only, and kept in a file of their own so that
fetching can never touch something you wrote.  Replying is not possible yet.

                                           *gauntlet-sending* *:GauntletPush*
:GauntletPush           Send the comments written since the last send, and
                        nothing else.  Asks for nothing and sends at once.

                                                              *:GauntletNote*
:GauntletNote           Write something about the pull request as a whole,
                        and send it -- with anything still unsent under it.

                                                           *:GauntletApprove*
:GauntletApprove        Approve the pull request.
                                                            *:GauntletReject*
:GauntletReject         Ask for changes.
                                                            *:GauntletSubmit*
:GauntletSubmit         Choose one of the four, when you have not decided
                        which yet.

Nothing leaves the machine until one of these.  Comments are written offline,
kept in the review directory, and go to GitHub as GitHub models a review: a
verdict, a covering note, and the line comments together.

|:GauntletPush| is the everyday one, and it asks for nothing: the comments say
what they have to say where they sit, and stopping to write a summary over
them is a toll on the common case.  The others open a buffer for the note --
`:w` sends, `:q` calls it off -- but none of them insists you write in it.  An
empty note is a review with no covering words, which is a perfectly ordinary
thing to leave.

                                                       *gauntlet-two-steps*
GitHub does demand a note when a review is created outright with a COMMENT or
REQUEST_CHANGES verdict.  A review created with *no* verdict does not need
one -- that is a draft, which nobody else can see -- and neither does the
verdict given to it afterwards.  So a send with nothing written over it goes
in two steps rather than one, which is what GitHub's own web interface does
when you start a review, add comments to it, and finish it.  Approving takes
one step either way, GitHub asking nothing of an approval.

Should the second step fail, the comments are sitting in a draft review on
GitHub.  Its id is kept, nothing is marked as sent, and the next send submits
that draft rather than starting another, so nothing is said twice.

Only comments you have not already sent go, so a verdict after a push carries
whatever was written since, and pushing twice in a row sends nothing the
second time.  Approving and rejecting therefore need no separate sync: the
comments ride along with the verdict, in the one request, and cannot be left
behind by a failure halfway.

Before anything is sent, two things are checked:

  - that every comment still sits on a line of the diff.  GitHub refuses a
    whole review over a single comment it will not place, taking the verdict
    and the other comments with it, so a comment whose line the pull request
    has since changed is named here instead, and nothing is sent.

  - that the branch has not moved since the review was opened.  Approving a
    pull request that is no longer the one on screen is the failure worth
    preventing.  Refreshing at that moment would swap the diff out from under
    a verdict just given, so this stops and asks for |:GauntletRefresh|.

If sending fails, nothing has left the machine: the comments are untouched
and the covering note is still in its buffer, so it can be written again once
whatever GitHub objected to is dealt with.  GitHub will not let you approve
your own pull request, and says so.

                                                  *gauntlet-comments-sent*
A comment that has been sent exists twice: as yours, here, and as a thread
fetched back from GitHub.  The fetched one wins -- it is the one that can
gain replies and be resolved -- so after a successful send the threads are
fetched again and the local copy is dropped.  It is dropped only once its
double has actually arrived, so a fetch that fails costs nothing: the comment
stays, marked as sent, until a later |:GauntletRefresh| finds it.

Comments are stored as *threads*, each holding a list of comments, even though
one you write has a single comment in it.  A thread fetched from GitHub is the
same shape with more comments and an author who is not you, so pulling threads
in later will add to this rather than change it.

                                                            *gauntlet-author*
ANSWERING A REVIEW OF YOUR OWN

Sometimes the quickest answer to a comment is the change it asks for.  When
the account `gh` is authenticated as is the pull request's author, the
right-hand pane is opened writable and `:w` writes the file in the review
worktree -- the same file a language server is already reading, so everything
that works for reading works for changing.

    :GauntletCommit     Commit what the worktree has changed.
    :GauntletPublish    Push it onto the pull request's branch.

|:GauntletCommit| opens a buffer for the message, listing what is about to go
in; `:w` commits, `:q` calls it off.  It stages everything, and refuses while
any pane still holds unwritten changes, since those would silently be left
out.  |:GauntletPublish| pushes to the branch by name -- the worktree is
detached, so there is nothing for a bare push to push to -- and then brings
the review's own record up to the commit it just sent, so a refresh
afterwards sees no movement.

Whose pull request it is, is worked out once and kept in `meta.json`, so
reconnecting to a review with no network still knows.  A review that never
recorded it stays read-only, which is the safe way to be wrong.

                                                      *gauntlet-unpublished*
The file list follows the worktree rather than the commit while a review is
yours, so an edit shows in the counts as soon as it is written -- including a
file you have just created, which `git diff` cannot see until it is staged.
Work that is not on GitHub is marked `✎`, against the file and in the header:

    ✎ 1 uncommitted
    ✎ 2 commits to publish

Two things follow from that.  A comment cannot be left on a file with
unpublished changes: its line numbers are not GitHub's, so the comment would
land somewhere else entirely.  And |:GauntletRefresh| will not reset a
worktree that holds work -- neither uncommitted changes nor commits that have
not been pushed -- it stops and says which.

Nothing gauntlet does tidily will discard an unwritten buffer, either:
switching files and redrawing both leave a modified pane exactly where it is.

A pull request from a fork has its branch in another repository, and the one
the review was fetched from is not it.  Publishing looks for that repository
among your remotes and, not finding it, says so rather than guessing.

8. THE REVIEW WORKTREE                                      *gauntlet-worktree*

A review is backed by a git worktree, so that it can be *started* online and
*finished* offline.  Opening a review does all the network work at once:
>
    git fetch origin refs/pull/<n>/head     the pull request's commits
    git merge-base <base> <head>            what it branched from
    git worktree add --detach <dir> <ref>   its files, on disk
    git diff <base> <head>                  every blob of both sides
<
That last step matters on a partial clone -- one made with `--filter` -- where
blobs are otherwise fetched only when something asks for them, and a review
would quietly need the network for every file opened.

Afterwards the file list and both sides of every diff are read from local git.

A review is kept at: >

    ~/.local/state/nvim/gauntlet/<repo>/pr-<n>/
        worktree/       the checkout, detached at the pull request's head
        comments.json   comments you have written but not yet sent
        threads.json    GitHub's own threads, cached
        meta.json       base and head commits, and when they were fetched
<
The worktree is a *subdirectory* of the review rather than the review itself,
so that nothing gauntlet writes ever appears in the worktree's `git status`,
where it could be committed by accident.

Reviews persist.  Opening one again reconnects to what is already on disk and
needs no network at all -- and so shows the commit it was opened at, however
much the branch has moved on since.  |:GauntletRefresh| is what fetches the
branch again and resets the worktree onto its current head.

                                                             *:GauntletDiscard*
:GauntletDiscard        Remove the current review from disk: its worktree, its
                        `refs/gauntlet/pr/<n>` ref, and gauntlet's own files.
:GauntletDiscard {id}   The same, for a review you are not looking at.

9. ERRORS                                                     *gauntlet-errors*

A review is labelled "PR Review {id}".  Neovim's own tabline and bufferline
style plugins both label from the tail of a buffer's name, so that is the tail
of the name; the repository is kept in front of it to stay unique, since two
repositories can each have a pull request #1.  The tab also carries the label
in the tab-scoped variable `t:gauntlet_title`.

The review takes a tab page of its own, leaving your window layout untouched.
The exception is when the only thing on screen is Neovim's own empty starting
buffer -- which is what |vig| leaves behind -- and the review takes that over
instead, rather than stranding a blank "[No Name]" tab beside itself.

The buffer is read-only, 'buftype' "nofile", and 'filetype' "markdown".

    q                   Close the review.  This closes its window, and so its
                        tab page; if the review was all that was open, as
                        after `vig {id}`, Neovim exits.


Both `:Gauntlet` and `vig` report:

  - Not inside a git repository.
  - The repository has no *open* pull request with that id.  A pull request
    that is merged or closed is reported the same way as one that never
    existed.
  - A URL that names a repository which is not a remote of the current one.
  - An argument that is neither a number nor a pull request URL.

Having no open pull requests at all is *not* an error: the list is empty.

A bare {id} is looked up against the repository's `upstream` remote if it has
one, and `origin` otherwise, so that working from a fork reviews the pull
requests of the project you forked.

10. CONFIGURATION                                      *gauntlet-configuration*

setup() takes an options table, merged over the defaults: >lua

    require("gauntlet").setup({
      gh = "gh",   -- path to the GitHub CLI
      limit = 100, -- most open pull requests to list at once
      dir = nil,   -- where review worktrees are kept; nil means
                   -- stdpath("state")/gauntlet
    })
<
Calling setup() is optional; the defaults apply without it.
